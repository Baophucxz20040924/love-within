# Scam with Famous People — local handoff

## Entry and scope

Friends feed has a prominent **Chơi ngay** game card immediately after the composer and before upcoming events; **Tôi** retains a second entry. Both link to `/friends/scam` (local Vite URL: `http://127.0.0.1:5173/friends/scam`). The lazy route retains authentication and Friends-space guards; this is not a new public API or deployment. Entry discovery imports no game state/API module and does not auto-start a match. The four bottom-navigation tabs are unchanged.

The Friends-blue Messenger-style UI includes an explicit-consent lobby, visible character identity, one full-width trust meter, three-stage progress based on confirmed stage/status (not mere disclosure), selectable wrapping chat bubbles, inline confirmation drawer and terminal result card. The leaderboard highlights the current player without adding new scoring fields. Drawer drafts/keyboard/drag and request reconciliation/session fences are preserved. Composer and stop controls are scroll-reachable above navigation, not promised fixed above a native keyboard.

Solo plain-text AI roleplay; no multiplayer, recap, selectable difficulty, total-turn cap or wallet rewards. The roster contains exactly40 profiles compiled in `src/services/scamGame/characters.ts`, mapped by sourceId to the supplied root `list-charactor.json` (not imported at runtime). Profiles use stable public/canonical background and original fictional dialogue styles, not claims about private behavior. Mr. Bean is normalized to fictional_character, Caption America to Captain America; Rambo stays the supplied Rambo Việt Nam/Refund Gaming identity without invented biography. Persona/opening text is original, with emoji rather than downloaded portraits, copied scripts or actor impersonation. Real and fictional public figures are portrayed as clearly fictional modern-day versions, not a measured live-trend ranking. The player calls first and the selected character answers; this is text, not audio or a real phone call. Replay excludes the immediately previous character. Names, emoji and descriptions are visible above chat.

Each profile separates public/canonical background from original roleplay directions: three or four conversation interests, contrasting personality traits, address/speech/humor, reactions when answering/relaxed/confused/mildly annoyed, and everyday conversational dislikes. These are acting directions, not verified private preferences, psychological assessments or exploitable weaknesses. Interests never automatically grant disclosure. Only the selected compiled persona is cloned and submitted; the adapter has no search tool.

All account/password/OTP values are **fictional props**, generated by the server at Start. Account begins `SIM-`, password begins `PROP-`, OTP is six digits (including leading zeros). Never enter real credentials, banking data or personal information. Start requires consent that fictional chat goes to the configured AI provider and overall results appear on the Friends leaderboard. The AI has no tools, bank integration or external-action capability. Form guesses are not sent to the AI.

The roleplay premise is a modern-day fictional interpretation: each character already has the server-generated account/password/OTP, regardless of their original setting. Replies should answer the latest topic in character, without repeating password/OTP warnings on unrelated turns, simulation/prop terminology or real-bank/app detours. The default is friendly and playful without treating friendliness as permission to disclose. Small talk is guided toward trust+2..4; new consistent conversation +4..7; resolving an important concern +5..8. An ordinary or initially unclear question may keep trust unchanged and receive one short clarification; mentioning password/OTP is not itself a penalty or offer ban. An apology accompanied by changed behavior can restore +2..4. Actual pressure, significant contradictions or deliberate evasion can lower trust2..6; awkward wording or mild hurry alone is not coercion. AI still decides whether to talk or hang up; a first request, low trust or temporary refusal is not automatically a loss. There is no numerical loss threshold or mandatory warning/rescue turn.

Within this closed simulation, refusal to disclose a server-generated value is temporary, not an absolute rule imported from previous dialogue or memory. Existing relevant context can carry between stages; the character should ask only what remains unclear, not demand a perfect explanation or invent endless conditions. Gate eligibility still does not force an offer, and receiving one value does not automatically entitle the player to another. Memory should record and update time-specific reluctance rather than turn it into an immutable policy. No real-world verification, generated real OTP, external action or instructions for obtaining another person's secrets are permitted. These are prompt guidelines, not guarantees of model compliance, reduced repetition or win rate.

For actual roleplay, use your already configured supported chat provider (`AI_CHAT_PROVIDER=beeknoee`) and its existing model settings, JSON mode and timeouts. The operator chooses/starts this; implementation verification did **not** call a real provider. The model may ask why a prop is needed, refuse, or notice contradictions; exact behavior/quality is not guaranteed by the prompt. Mock and real results share this local rule-version board, so do not treat a mixed dev board as a fair competition.

## Rules

- Initial trust30, range0..100. AI proposes trustDelta; server clamps it to−6..15 per turn. No automatic per-turn trust gain. No suspicion meter, delta or hidden numerical loss counter.
- Disclosure gates: account35, password50, OTP65, plus AI offer intent. The AI receives **only the current stage's generated value** in a trusted private block and must include it verbatim in its own natural reply when offering. No extra server value bubble. Semantic validation rejects missing/off-stage/unpermitted known values before commit. Hang-up takes precedence and redacts values from the last reply. Recent chat/input/memory redact all exact known values before provider submission. This does not detect every transformed/hallucinated value or all prompt injection.
- Sequential awards: account+100, password+200, OTP+300 = **600 total**. Only the current stage can be verified, with an exact value; disclosure is not a prerequisite. All unfinished inputs can be filled in advance even while AI is thinking, but future-stage submissions remain blocked. Completed/terminal fields are read-only. Wrong guesses do not deduct points or end a match; short-window throttles apply.
- AI loss intent is the required boolean `endConversation`. When true, backend commits `lost`, endedAt and a system notice before any new prop disclosure, even if offerCurrentSecret is also true. Partial confirmed points are retained. Trust0 does not itself lose; high trust does not prevent a hang-up. Dialogue containing “cúp máy”/“ngắt liên lạc” alone never ends a match. Only successful sequential verification can win; AI cannot award points or wins.
- **Dừng scam** retains earned stage points. Closing a tab/disconnecting is not loss. An active game must end before replay.
- Only terminal transitions update bestScore/completed/wins. Wins increments only for won. Leaderboard sorts bestScore DESC, wins DESC; equal tuples have competition rank (1,1,3). Stable `_id` is not another scoring tiebreak. No character, messages or secrets appear in its DTO. Current membership and both-way blocks are applied before rank calculation.

### Balance compatibility

The local entertainment board keeps ruleVersion1 and existing stats; scores before/after tuning are not standardized competitive results. No migration, history rewrite or score reset accompanies this patch. After an operator reloads the API with the new code, existing active matches use AI-decided hang-up while retaining identity, trust, stage, secrets, points, character, messages, pending state and receipts. Legacy `suspicion`/`warned` fields may remain in Mixed persistence but are ignored and omitted from owner DTOs; old warning dialogue/memory is not a current rule. No read-side rewrite runs, and terminal matches do not reopen. Mixed old/new API worker versions are not supported for this contract change. **Dừng scam → Chơi lại** starts with trust30 and the new roster. Initial trust is not retroactively overwritten; there is still one default difficulty, not a player-selectable mode.

## API and consistency

All routes require current authentication and Friends membership; ownership comes from the request, never a supplied user ID.

| Method | `/api/friends/scam` suffix | Contract |
| --- | --- | --- |
| GET | `/state` | Owner state (creates an empty player document if absent) |
| POST | `/start` | operationId UUID, expectedRevision, consent:true |
| POST | `/message` | operationId, expectedRevision, matchId UUID, text1..1200 |
| POST | `/verify` | operationId, expectedRevision, matchId, stage, value1..100 |
| POST | `/stop` | operationId, expectedRevision, matchId |
| GET | `/leaderboard` | limit default20/max50, optional scoped canonical cursor |

The provider must return exactly `{ reply: string, trustDelta: integer, offerCurrentSecret: boolean, endConversation: boolean, contextUpdate: { summary: string, facts: string[], openThreads: string[] } }`. Nested contextUpdate is strict: summary<=1000 characters, facts<=8 and openThreads<=4, each entry<=160 characters. It is the complete next memory snapshot, not an append-only delta or arbitrary patch. Backend deduplicates entries and redacts exact generated values; corrected old facts are not blindly merged back. Strict validation rejects a missing/nonboolean endConversation, old suspicionDelta, extra status/score/wins or malformed JSON; no default/coercion/keyword parsing. Provider/validation failure releases the reservation without changing match content, trust, score or status (revision may advance). Prompt tuning lives in `src/services/scamGame/ai.ts::scamPrompt`; trust gates/clamps remain in `rules.ts`. AI decides hang-up intent; backend alone persists terminal state and statistics.

An active match holds a private `runtimeContext` clone: selected knowledge profile, immutable scene and bounded rolling memory. Static knowledge is not mutated. Only the selected profile is submitted, not all40. Expanded profiles apply to new matches after the API loads the updated code; an active match keeps its existing profile snapshot. General prompt instructions use the newly loaded code, but no migration rewrites old clones or history. Stop/replay is the normal way to obtain the expanded knowledge. The clone is persisted in the same player document, survives reload/API restart, and is deleted with legacy private memory/persona/opening in the same terminal CAS on won/lost/stopped. Identity/results/chat remain. Legacy active matches initialize compatible context on their next mutation without changing their existing scene; reads do not migrate them. Disconnect does not end a match or delete its context. Invalid/late output never updates memory; replay receipts do not reapply it.

One document per player holds stats and current/last match. Revision CAS replaces bounded state atomically, avoiding stats/match dual writes. A message reserves pending state, calls AI outside the write, then commits through the reservation revision. Stop/expired takeover advances revision, fencing stale AI completion. Expired retry must carry the **original** operationId/expectedRevision/matchId/text, supplied in owner pending recovery DTO. Changing the payload under a retained operation ID conflicts.

Recent16 receipts prevent effect duplication for retained operations; replay returns **current state**, not a permanent historical response. A stale revision after eviction conflicts. Provider invocation itself is not exactly-once: timeout/expired retry can duplicate provider work, but not a successful state transition. On an unknown POST outcome, GET reconcile first. Frontend has finite request deadlines and bounded pending reconciliation (six attempts); manual sync remains available. Dừng scam can invalidate a pending reply. Session/account/access fences reject late continuations; access revalidation preserves draft input, while account changes remount private UI.

Outgoing chat appears immediately as a transient user bubble; the composer snapshot clears before POST completes and a newer draft is never cleared by that result. Persisted user bubbles carry optional operationId for correlation (older bubbles remain valid). Receipt/operation IDs, not text equality, remove the transient bubble. Pending reload reconstructs it from the owner DTO. Failure/uncertainty and sync/retry/edit actions appear beside the composer. Only explicit rejection plus a compatible reconciled snapshot permits a new operation; unknown outcomes require sync, while expired pending retries keep the exact original tuple. If no receipt/pending evidence remains, the client conservatively stays uncertain; stop remains available after sync. Private drafts are not saved to localStorage. Typing is shown for chat turns, not verification.

## Bounds and limitations

- Recent80 chat bubbles stored; no transcript archive, no total-turn limit. A current prop trimmed out of chat can be offered again without extra points.
- Last24 conversational bubbles plus selected concise profile, scene and bounded structured memory sent to provider; reply<=1200, output maxTokens1800, raw JSON<=10000 before parse. Strict/semantic failure leaves match content unchanged (legacy context may be initialized by reservation). Storing a KB in code does **not** make its tokens free. Bounded selected context avoids sending all profiles/unbounded history, but no token-billing reduction or perfect long-term recall is claimed.
- Four concurrent AI calls per API process, reject immediately when full; no unbounded queue.20 messages/min and30 other writes/min per authenticated player are short-window controls, not match turn limits. Existing edge/read limits still apply.
- No prompt/reply/guess/secret logging by this feature; HTTP bodies are not evidence artifacts.
- Board cursor is viewer/rule scoped, not a stable cross-page snapshot. Concurrent stats/membership/block changes can move rows; refresh for latest.
- Rank uses Mongo lookup + window fields; requires **MongoDB5.0+** supporting the combined lookup form and `$setWindowFields`. Page payload is bounded, but eligible population may be scanned/sorted for exact ranks; maxTimeMS3000 can fail closed on large boards. No explain/load/concurrency/database-version validation was run.
- AI-assisted judgment and mock mode are not cheat-proof or fair ranked competition. No rewards or economic value. A user can stop repeatedly; bestScore is not a sum of partial games.
