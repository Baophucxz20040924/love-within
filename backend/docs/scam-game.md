# Scam with Famous People — local handoff

## Entry and scope

Both link to `/friends/scam` (local Vite URL: `http://127.0.0.1:5173/friends/scam`). The lazy route retains authentication and Friends-space guards; this is not a new public API or deployment. Entry discovery imports no game state/API module and does not auto-start a match. The bottom navigation is hidden only inside the game; **← Hội bạn bè** returns to the normal Friends shell.

The Friends-blue Messenger-style UI includes an explicit-consent lobby, visible character identity, one full-width trust meter, two- or three-step progress based on confirmed stage/status (not mere disclosure), selectable wrapping chat bubbles, inline confirmation drawer and terminal result card. The leaderboard highlights the current player without adding new scoring fields. **Time to scam** focuses on chat and confirmation; the leaderboard button/component is available only after a server-confirmed won/lost/stopped match, not in the lobby or during play. An accepted active snapshot resets a stale board tab. The compact workspace shows one selected confirmation form, switched by click/tap/Enter/Space, with no pointer capture. Drafts and request reconciliation/session fences are preserved. Small-height/enlarged-text controls remain scroll-reachable, not promised fixed above a native keyboard.

Solo plain-text AI roleplay; no multiplayer, recap, selectable difficulty, total-turn cap or wallet rewards. The roster contains exactly40 profiles compiled in `src/services/scamGame/characters.ts`, mapped by sourceId to the supplied root `list-charactor.json` (not imported at runtime). Profiles use stable public/canonical background and original fictional dialogue styles, not claims about private behavior. Mr. Bean is normalized to fictional_character, Caption America to Captain America; Rambo stays the supplied Rambo Việt Nam/Refund Gaming identity without invented biography. Persona/opening text is original, with emoji rather than downloaded portraits, copied scripts or actor impersonation. Real and fictional public figures are portrayed as clearly fictional modern-day versions, not a measured live-trend ranking. The player calls first and the selected character answers; this is text, not audio or a real phone call. Replay excludes the immediately previous character. Names, emoji and descriptions are visible above chat.

Each profile separates public/canonical background from original roleplay directions: three or four conversation interests, contrasting personality traits, address/speech/humor, reactions when answering/relaxed/confused/mildly annoyed, and everyday conversational dislikes. These are acting directions, not verified private preferences, psychological assessments or exploitable weaknesses. Interests never automatically grant disclosure. Only the selected compiled persona is cloned and submitted; the adapter has no search tool.

All account/password/OTP values are **fictional props**, generated by the server at Start. New accounts are `SIM-` plus four uppercase hexadecimal characters (8 total); passwords are `P-` plus six uppercase letters/digits from `ABCDEFGHJKLMNPQRSTUVWXYZ23456789` (8 total); OTP is six digits (including leading zeros). Shorter entropy is an intentional convenience for this reward-free game, never a real authentication scheme. Verification is scoped to owner/match/stage; global uniqueness is not required. Existing matches keep their original values and inputs still accept up to100 characters. Never enter real credentials, banking data or personal information. Start requires consent that fictional chat goes to the configured AI provider and overall results appear on the Friends leaderboard. The AI has no tools, bank integration or external-action capability. Form guesses are not sent to the AI.

## Rules

- Initial trust30, range0..100. AI proposes trustDelta; server clamps it to−12..20 per turn. No automatic per-turn trust gain. No suspicion meter, delta or hidden numerical loss counter.
- Disclosure gates: account35, password50, OTP65, plus AI offer intent. The AI receives **only the current stage's generated value** in a trusted private block and must include it verbatim in its own natural reply when offering. No extra server value bubble. Semantic validation rejects missing/off-stage/unpermitted known values before commit. Hang-up takes precedence and redacts values from the last reply. Recent chat/input/memory redact all exact known values before provider submission. This does not detect every transformed/hallucinated value or all prompt injection.
- Sequential awards follow the scenario table above; bank remains account+100, password+200, OTP+300 = **600$ base**, plus30–150$ on winning. Only the current stage can be verified using its comparison policy; disclosure is not a prerequisite. All unfinished inputs can be filled in advance even while AI is thinking, but future-stage submissions remain blocked. Completed/terminal fields are read-only. Wrong guesses do not deduct points or end a match; short-window throttles apply.
- AI loss intent is the required boolean `endConversation`. When true, backend commits `lost`, endedAt and a system notice before any new prop disclosure, even if offerCurrentSecret is also true. Partial confirmed points are retained. Trust0 does not itself lose; high trust does not prevent a hang-up. Dialogue containing “cúp máy”/“ngắt liên lạc” alone never ends a match. Only successful sequential verification can win; AI cannot award points or wins.
- **Dừng scam** retains earned stage points. Closing a tab/disconnecting is not loss. An active game must end before replay.
- Only terminal transitions update bestScore/completed/wins. Wins increments only for won. Leaderboard sorts bestScore DESC, wins DESC; equal tuples have competition rank (1,1,3). Stable `_id` is not another scoring tiebreak. No character, messages or secrets appear in its DTO. Current membership and both-way blocks are applied before rank calculation.

## API and consistency

All routes require current authentication and Friends membership; ownership comes from the request, never a supplied user ID.

| Method | `/api/friends/scam` suffix | Contract |
| --- | --- | --- |
| GET | `/state` | Owner state (creates an empty player document if absent) |
| POST | `/start` | operationId UUID, expectedRevision, consent:true |
| POST | `/message` | operationId, expectedRevision, matchId UUID, text1..1200 |
| POST | `/verify` | operationId, expectedRevision, matchId, stage, value1..100 |
| POST | `/stop` | operationId, expectedRevision, matchId |
| GET | `/leaderboard` | limit default20/max50, optional scoped canonical cursor |

The provider must return exactly `{ reply: string, emotion: ScamEmotion, trustDelta: integer, offerCurrentSecret: boolean, endConversation: boolean, contextUpdate: { summary: string, facts: string[], openThreads: string[] } }`. Nested contextUpdate is strict: summary<=1000 characters, facts<=8 and openThreads<=4, each entry<=160 characters. It is the complete next memory snapshot, not an append-only delta or arbitrary patch. Backend deduplicates entries and redacts exact generated values; corrected old facts are not blindly merged back. Strict validation rejects a missing/nonboolean endConversation, old suspicionDelta, extra status/score/wins or malformed JSON; no default/coercion/keyword parsing. Provider/validation failure releases the reservation without changing match content, trust, score or status (revision may advance). Prompt tuning lives in `src/services/scamGame/ai.ts::scamPrompt`; trust gates/clamps remain in `rules.ts`. AI decides hang-up intent; backend alone persists terminal state and statistics.

An active match holds a private `runtimeContext` clone: selected knowledge profile, immutable scene and bounded rolling memory. Static knowledge is not mutated. Only the selected profile is submitted, not all40. Expanded profiles apply to new matches after the API loads the updated code; an active match keeps its existing profile snapshot. General prompt instructions use the newly loaded code, but no migration rewrites old clones or history. Stop/replay is the normal way to obtain the expanded knowledge. The clone is persisted in the same player document, survives reload/API restart, and is deleted with legacy private memory/persona/opening in the same terminal CAS on won/lost/stopped. Identity/results/chat and generated values remain in the current/last match until it is replaced by replay; terminal cleanup does not delete the whole match. Legacy active matches initialize compatible context on their next mutation without changing their existing scene; reads do not migrate them. Disconnect does not end a match or delete its context. Invalid/late output never updates memory; replay receipts do not reapply it.

One document per player holds stats and current/last match. Revision CAS replaces bounded state atomically, avoiding stats/match dual writes. A message reserves pending state, calls AI outside the write, then commits through the reservation revision. Stop/expired takeover advances revision, fencing stale AI completion. Expired retry must carry the **original** operationId/expectedRevision/matchId/text, supplied in owner pending recovery DTO. Changing the payload under a retained operation ID conflicts.

Recent16 receipts prevent effect duplication for retained operations; replay returns **current state**, not a permanent historical response. A stale revision after eviction conflicts. Provider invocation itself is not exactly-once: timeout/expired retry can duplicate provider work, but not a successful state transition. On an unknown POST outcome, GET reconcile first. Frontend has finite request deadlines and bounded pending reconciliation (six attempts); manual sync remains available. Dừng scam can invalidate a pending reply. Session/account/access fences reject late continuations; access revalidation preserves draft input, while account changes remount private UI.

Outgoing chat appears immediately as a transient user bubble; the composer snapshot clears before POST completes and a newer draft is never cleared by that result. Persisted user bubbles carry optional operationId for correlation (older bubbles remain valid). Receipt/operation IDs, not text equality, remove the transient bubble. Pending reload reconstructs it from the owner DTO. Failure/uncertainty and sync/retry/edit actions appear beside the composer. Only explicit rejection plus a compatible reconciled snapshot permits a new operation; unknown outcomes require sync, while expired pending retries keep the exact original tuple. If no receipt/pending evidence remains, the client conservatively stays uncertain; stop remains available after sync. Private drafts are not saved to localStorage. Typing is shown for chat turns, not verification.

## Character emotions

Each accepted AI turn returns a required `emotion` enum alongside reply/trustDelta: `neutral`, `happy`, `excited`, `amused`, `confident`, `grateful`, `curious`, `thoughtful`, `confused`, `embarrassed`, `worried`, `skeptical`, `annoyed`, `angry`, `disappointed`, `sad`. All40 fictional profiles have distinct emotional-expression directions; these are tendencies, not character-specific whitelists. Any role can express any of the16 states when context supports it. The prompt asks for continuity and expression in the reply, not random badge changes. These directions are fictional, not psychological claims about real people.

Emotion is independent of trust: anger does not automatically lose, happiness does not grant disclosure, and skepticism does not reintroduce a suspicion meter. Only `endConversation` ends a losing match. New matches start neutral; missing/invalid legacy persisted values display neutral without a read-side write. New model outputs must supply a valid enum; missing/invalid emotion uses the existing bounded schema-repair path, not a silent fallback. New profile directions apply to new clones; old matches keep their snapshots.

The owner DTO exposes the last committed emotion. A labeled icon near the character name updates with the canonical turn response, not while the model is still thinking. Pending/failed turns keep the previous emotion; reload restores it. CAS/receipt/access fences prevent duplicate or stale updates. Verification/stop retain the last emotion; terminal UI labels it “Cảm xúc cuối”; replay resets it. Emotion stays in the last match after private context cleanup, never in the leaderboard. There is no new streaming connection, timer, poll, provider call, free-text emotion label or extra scoring rule. Mock ordinary/hang-up replies use happy/angry deterministically; they do not simulate character psychology.

## AI failure recovery and diagnostics

A game turn now owns a maximum of **two provider HTTP attempts total**, including either one transient-provider retry or one output-repair attempt. Adapter retries are disabled for this caller to prevent retry multiplication; other callers retain their existing retry policy. Game provider time is bounded to `min(75000, 2 * configured chatTimeoutMs)` with each call capped by the configured timeout and remaining budget; no retry starts with less than1000ms remaining. The frontend still uses90s, and the reservation lease/CAS fencing is unchanged. This leaves headroom for normal processing but does not guarantee a deadline for database operations; GET reconciliation still handles unknown outcomes.

JSON syntax, strict schema, current-stage disclosure validation and `finish_reason:length` may trigger one fresh completion with a static correction hint. Invalid raw output is never appended to the prompt, committed to chat/memory or logged. A single JSON code fence around the entire response is accepted; prose-wrapped or concatenated objects are not. Required booleans, strict memory shape, exact current value/gate checks and terminal handling remain mandatory. No automatic secret insertion, fabricated fallback reply, silent memory reset or score adjustment is used. Oversized output, timeout, configuration/auth failures and explicit provider refusal/content filtering do not trigger repair. Shorter memory is encouraged (summary target400 characters) without changing stored schema bounds or maxTokens1800. Refusal detection relies on provider metadata, not keyword inference from arbitrary dialogue.

Static `Scam AI attempt failed` / `Scam AI attempt recovered` events carry safe code/outcome, attempt number, elapsedMs and responseChars, with existing request correlation. They never include prompts, chat, profiles, memory, generated values, raw provider messages or Zod issues. Codes distinguish timeout/network/rate_limit/upstream/configuration/auth/invalid_response/empty_response and JSON/schema/disclosure/length failures. The public code remains `SCAM_AI_UNAVAILABLE` for compatible explicit-rejection reconciliation, but Vietnamese messages distinguish timeout, service failure and invalid output. No blind frontend repost is added. Actual frequency and dominant failure cause require runtime observations; offline fixtures do not establish them.

## Bounds and limitations

- Recent80 chat bubbles stored; no transcript archive, no total-turn limit. A current prop trimmed out of chat can be offered again without extra points.
- Last24 conversational bubbles plus selected concise profile, scene and bounded structured memory sent to provider; reply<=1200, output maxTokens1800, raw JSON<=10000 before parse. Strict/semantic failure leaves match content unchanged (legacy context may be initialized by reservation). Storing a KB in code does **not** make its tokens free. Bounded selected context avoids sending all profiles/unbounded history, but no token-billing reduction or perfect long-term recall is claimed.
- Four concurrent AI calls per API process, reject immediately when full; no unbounded queue.20 messages/min and30 other writes/min per authenticated player are short-window controls, not match turn limits. Existing edge/read limits still apply.
- No prompt/reply/guess/secret logging by this feature; HTTP bodies are not evidence artifacts.
- Board cursor is viewer/rule scoped, not a stable cross-page snapshot. Concurrent stats/membership/block changes can move rows; refresh for latest.
- Rank uses two aggregations with classic equality lookups, not window stages: bounded seek page (`limit+1`), then at most50 grouped score/wins counters over the same eligibility. Eligibility is viewer plus accepted direct friends with current Friends membership and completed games, excluding both-way blocks. No5000-friend helper cap. Each query has maxTimeMS3000; eligible population can still be scanned/sorted, and the two reads are not a transaction snapshot. Cursor scope is `friends-v2`; old cursors are rejected. Timeout/unavailable errors are safe503 codes with a request reference, not empty results. No live Mongo syntax, explain/load/concurrency or production failure-cause validation was run.
- AI-assisted judgment and mock mode are not cheat-proof or fair ranked competition. No rewards or economic value. A user can stop repeatedly; bestScore is not a sum of partial games.
